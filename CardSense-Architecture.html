01What CardSense is

CardSense reads a user’s spending, matches it against the reward rules of the cards they actually hold, and tells them which card to use and when. It runs on its own schedule and pushes conclusions. The user is never required to ask it anything.

The product exists because credit card reward terms are deliberately hard to hold in your head: rates vary by merchant category, most bonus rates are capped, caps reset on cycles that differ per card, and the value of a point depends on how you redeem it. A person optimising by hand would need to re-derive the answer at every checkout. Nobody does. The money quietly goes to the wrong card.

Explicit non-goals

  • Not a chatbot. There is no conversational surface in the primary flow. The system reports; it does not wait to be asked.
  • Not transactional. CardSense never moves money, never autofills a payment form, and never stores a card number. This is an architectural boundary, not an unimplemented feature — it removes PCI scope from the system entirely.
  • Not intended as a generic comparison site. The current catalogue is descriptive and marks held cards, but new-card deltaVsWallet simulation is not implemented yet.

What the user contributes

Three declarations, and nothing else: the accounts they spend from, the terms documents for cards they hold, and a goal. Optionally, spending they know is coming — a trip, a large purchase — which the system cannot infer from history.

02Architectural principles

Six decisions that everything else follows from. They are the answer to why is it built this way.

1 · Agents coordinate through shared state, never direct calls

Each agent reads the collections it needs and writes only its own. No agent invokes another. The consequences are what matter: incomplete input can degrade a stage visibly; two developers can own different agents without coupling their business logic; and every completed run is auditable after the fact. Stage-specific replay is not implemented yet.

2 · The language model never computes a number that appears as money

Gemini reads documents and writes prose. Deterministic code does arithmetic. This is non-negotiable in a product whose core accountability screen compares predicted against actually earned — a hallucinated forecast would be caught by our own reporting. It also means every figure is reproducible from the same inputs, which is the difference between a financial tool and a demo.

3 · One read model

The interface reads a single denormalised document rather than joining eight collections. A projection step is the only component that knows the shape the UI expects, which leaves the agents free to evolve their own schemas without touching a line of frontend code.

4 · Degradation is visible and actionable, never silent

When a terms document fails to parse, that card is excluded from every comparison, the interface says so on the card itself, and it offers the action that fixes it. A financial tool that quietly guesses is worse than one that admits what it could not read.

5 · The advisory layer is held to account

Every recommendation is stored with the value it predicted and the interface can display predicted-versus-actual records. Automatic period-close reconciliation and threshold learning are not implemented yet; the current track record is the contract and UI foundation for that loop.

6 · Provenance is a feature, not a debug view

Every reward rate traces to a source document, a location within it, the date it was read, and the date it will next be rechecked. Every recommendation carries the chain of agents that produced it, with the figures each one used.

04The five agents

Two of the five are driven by Gemini. Three are deliberately not. Choosing correctly between them is the single most consequential decision in this architecture.

1 · Ingestion Deterministic

Connects to Plaid in sandbox mode and pulls transactions incrementally, normalising them into a category taxonomy the rest of the system can reason about.

Reads
Plaid /transactions/sync · mcc_map
Writes
transactions · agent_runs

How it works

  • Uses Plaid’s /transactions/sync endpoint rather than a date-range fetch. It returns added, modified and removed records against a cursor, which makes ingestion incremental and idempotent — re-running it never double-counts.
  • The cursor is stored per linked item, so each run only fetches what changed.
  • Merchant and category data are normalised through a mapping table (see below), then grouped into the categories the reward rules are written against.
  • Merchants that could plausibly map to more than one category are flagged rather than resolved, with the value at stake between interpretations recorded.

Why no language model

This is a fetch, a join and a group-by. A model here would add latency, introduce non-determinism into the foundation every downstream figure rests on, and risk inventing transactions that do not exist.

Known integration risk

Plaid returns its own category taxonomy, not the merchant category codes that issuer terms are written in. A maintained mapping table sits between the two. This is small — roughly one row per supported category — but it must be built early, because every downstream number depends on the join being right.

2 · Card Intelligence Gemini

Reads the issuer’s own terms — a PDF or a web page — and extracts the structured reward rules: which category, what rate, what cap, on what cycle. Rechecks on a schedule so that a rate change propagates without anyone noticing manually.

Reads
Terms PDFs and pages (user-supplied)
Writes
card_rules · agent_runs

How it works

  • Gemini’s document understanding parses the source into a strict schema — category, rate, cap, cycle — rather than free text, so downstream code can rely on the shape.
  • Multimodal handling matters here. A meaningful fraction of card terms are distributed as scanned images with no text layer. Vision-capable extraction is what makes those readable at all.
  • Extraction confidence is recorded alongside the rules. Low confidence is treated as a failure, not a result.
  • Every rule retains its provenance: the document, the page or URL, and the timestamp it was read.

Failure handling

If a document cannot be read with confidence, the card is excluded from every comparison rather than guessed at, the interface states why, and the user is offered manual rate entry as a recovery path. If a source rate-limits, the previously extracted rules are retained but marked stale with the date of the last successful read.

Why this is global, not per-user

Reward rules belong to the card, not the cardholder. Parsing an issuer’s terms once serves every user of the system, and the card catalogue becomes a by-product of work already done rather than a separate feature.

3 · Forecast Mostly deterministic

Projects near-term spending, and — more usefully — identifies the specific future dates on which the right card changes.

Reads
transactions · planned · card_rules
Writes
forecasts · agent_runs

How it works

  • Projects a spending range from recent history, stated with an explicit confidence band rather than a false point estimate.
  • Merges in spending the user has declared — a trip, a large purchase — which no amount of history could have predicted.
  • Detects cap collisions. Given a projected or declared amount in a category, it determines whether the best card’s cap will be breached, on what date, by how much, and how the spend should be split. This is where the forecast stops being analytics and starts being instruction.
  • Emits a dated timeline: cap crossings, bonus deadlines, cycle resets, declared events, and scheduled agent rechecks.

What it deliberately does not do

It does not claim seasonality. Sandbox transaction history is too thin to support that claim honestly, and the interface says as much on screen. A language model is used only to interpret free-text declarations such as “Lisbon trip, 19–22 August” into structured dates, amounts and categories.

4 · Simulation & Strategy Deterministic — strictly

The optimiser. Prices every card against every category of actual spending and computes the gap between what was earned and what the best available choice would have earned.

Reads
transactions · card_rules · forecasts · goal
Writes
strategy_runs · agent_runs

How it works

  • Three-track normalisation. Points, cash back and air miles are not comparable until priced in dollars. Every track is converted to nominal value at a stated rate, and that assumption is displayed in the interface rather than buried in a constant.
  • Cap-aware simulation: a card stops being the best choice the moment its cap is reached, so headroom is tracked per card per cycle and factored into every ranking.
  • Where two cards score within a cent of each other, the result is recorded as a tie. The system does not invent a winner where none exists; it surfaces the human-judgeable tiebreaker instead.
  • When a goal exists, it also computes pace: current balance, earning rate, projected arrival date against the deadline, and the single change that most improves that date.

Why this agent must never use a language model

Every dollar figure the user sees originates here. Those figures are compared, later, against what the transactions actually returned — on a screen built specifically to expose the difference. A generated number would make that comparison meaningless, and would be caught by our own reporting. Determinism here is what makes the accountability loop in section 2.5 possible at all.

5 · Advisory Gemini

Turns the optimiser’s output into something a person can act on, and takes responsibility for what it recommended.

Reads
strategy_runs · advice (history)
Writes
advice · agent_runs

How it works

  • Writes each recommendation as an imperative with its cost of inaction, ranked by dollars at risk before the nearest deadline rather than by raw size.
  • Composes the reasoning trace: which agent contributed what, with the figures each one used. This is what makes a recommendation checkable instead of merely asserted.
  • Constrained to describe only numbers it was handed. It has no arithmetic authority.
  • Records the predicted value and user outcome with each recommendation so a later reconciliation process has an accountable baseline.
  • Respects stored open, acted and dismissed outcomes. Automatic threshold adjustment and expiry-driven learning remain future work.

05Data architecture

  ├─ goal                 user-written  · read by Strategy

  ├─ agent_runs/{runId}   every agent · powers the activity log
  └─ snapshots/current    ◀── THE READ MODEL

card_rules/{cardId}       global — parsed once, serves every user
mcc_map/{category}        Plaid taxonomy → our categories → issuer wording

The read model

Rather than have the interface join eight collections, a projection step composes a single document matching exactly the shape the frontend expects. The interface performs one read. The benefits compound: no waterfall requests, no join logic in components, and a single place that must change when either side evolves.

The document holds aggregates only — categories, cards, recommendations, a truncated run log — so it remains far inside the platform’s document size limit regardless of how many transactions accumulate underneath it.

Two deliberate choices

  • Card rules are global. They belong to the card, not the holder. This makes parsing work once and serve everyone.
  • Credentials are unreadable by any client. Access tokens live in a collection denied to the browser outright and touched only server-side. A token reaching a client is the one unrecoverable failure in this design, so it is prevented structurally rather than by convention.

06Frontend architecture

Next.js 16 (App Router), React 19, TypeScript, Tailwind v4. Server components by default; client components only where the user provides input.

The contract

Every page reads one typed Snapshot object from FastAPI through a shared server-side loader. Development fixtures are used only when explicitly enabled; production fails visibly if the backend is unavailable. Browser mutations pass through a Next.js proxy that invalidates the tagged snapshot cache.

The write path

Three places where the user gives the system something, each placed with the agent that consumes it rather than collected in a settings page — because two of the three are worth nothing without immediate feedback:

  • Adding a card sits on the cards page. Extraction runs visibly, then the rules it found are shown for correction before they drive anything.
  • Planned spending sits against the timeline it changes. Declaring a purchase recalculates the projection and, if it would breach a cap, inserts the collision as a new dated warning.
  • The goal has its own surface. Pace, projected arrival and the shortfall recompute live as the fields change.

Recommendations can be marked done or dismissed, which is what feeds the accountability record. No state is a dead end: an unset preference, unread rules and stale rules each offer the action that resolves them.

Design system

A single palette carries meaning rather than decoration. Brass is reward that went unclaimed; verdigris is reward banked; ember marks states needing attention. One bar grammar — solid for earned, hatched for missed — runs at two scales: full width in the hero, repeated small for every category. Categories sort by reward missed rather than amount spent, because the largest category is rarely the largest leak.

07Chrome extension

Manifest V3 prototype. A content script can identify the merchant and whether the current page looks like a checkout, but the popup is not wired to that script or to the backend. Its recommendation is fixed demo data until a live merchant-recommendation endpoint is connected.

The hard boundary

The extension states, directly above the point where a user would type their card number: CardSense never fills or stores a card number. The user selects and enters their own card. This is why it requires only activeTab and no payment-related permissions — there is no payment surface to attack.

08Deployment topology

The intended deployment topology is two Cloud Run services, both scaling to zero when idle:

  • web — the Next.js application, serving the dashboard.
  • agents — FastAPI with the built-in orchestrator as the default and ADK as an experimental engine.

Firestore provides persistent state in non-demo mode; the JSON-backed local store provides the same interface in demo mode. Onboarding polls the run-status API. Plaid sync completes one real analysis run, and step 3 reuses it after a targeted goal write instead of launching a duplicate run.

Scaling to zero matters beyond cost: an agent system that idles for free is one that can run on a schedule indefinitely without a standing bill, which is the deployment shape this product actually needs.

09Security & privacy

  • Plaid access tokens never leave the server. The collection holding them is unreadable by any client, enforced in security rules rather than by convention.
  • No card numbers are stored, transmitted, or entered anywhere in the system.
  • The browser uses the Next.js backend proxy; server components load the snapshot directly from FastAPI.
  • A visible disclaimer states the product is informational and not licensed financial advice.
  • Sandbox data only. No production financial connection exists.
  • Current limitation: application authentication, multi-user authorization, and Plaid webhook signature verification are not implemented. The fixed demo-user runtime must not be exposed as a shared production service.

How each criterion is addressed

Innovation & operational utility

Two things here are genuinely uncommon. First, the system acts before the fact — a declared trip produces a dated warning that a cap will be breached mid-journey, with the split to make instead. Second, the system is accountable: it records what it predicted and reports what actually happened, including its own misses. Most tools of this kind make claims; this one is checkable.

Architectural discipline & tech stack

Five stages coordinating through shared state with no direct agent-to-agent calls; a deliberate boundary between model work and deterministic arithmetic; a single read model; and an experimental ADK graph whose remaining parity gaps are explicit.

Demo & production readiness

A run log showing actual stage execution, duration, reads, writes and degraded input; visible empty and failure states; and an architecture document that states plainly what is built and what is not.

13Known limitations

  • Conversion rates are placeholders. Points and miles are priced at assumed rates pending confirmation against issuer transfer charts. The interface states this on screen rather than presenting them as settled.
  • Forecast is trend-based, not seasonal. Sandbox history is too thin to support a seasonality claim, and we do not make one.
  • Card coverage is a fixed seeded set — roughly eight to ten cards — not open-ended scraping.
  • Category mapping is maintained by hand. Plaid’s taxonomy does not map one-to-one onto the codes issuer terms are written in.
  • Sandbox data only. No production financial connection, by design and by scope.
  • Single user. Authentication and multi-tenancy are designed for but not implemented.
  • Reward simulation is not issuer-complete. Every card condition, minimum spend, channel restriction and statement-cycle boundary is not yet enforced transaction by transaction.
  • ADK is experimental. The built-in orchestrator remains the default until persistence and output parity are proven.
  • The extension is not live. Its detector and UI exist, but the displayed verdict is fixed demo data.
  • Background jobs are in-process. FastAPI background tasks are not a durable Cloud Tasks or Pub/Sub queue.

14Original build plan

Historical section

This is the original August build plan retained for context. Section 12, not the milestones below, is the source of truth for current implementation status.

Two people. Twenty-three days. Both new to this stack. The plan below is shaped around one conviction: the way teams lose a hackathon is not by building too little, it is by having nothing that runs until the final week.

The single most important idea in this plan

On day three — before a single agent exists — copy the placeholder values into the database by hand, point the frontend at it, and deploy. You will have a live, recordable demo running on real infrastructure with fake numbers. From that moment you always have something to submit, and every subsequent step is an improvement rather than a gamble. Replace one agent’s contribution at a time after that.

Before anything else — your first three hours

  1. Both of you: get the existing frontend running locally. npm run setup then npm run dev. Click every page. This is the thing you are building a backend for; know it.
  2. Create one Google Cloud project. One. Share it. Enable Firestore, Cloud Run and the Gemini API.
  3. Create a Plaid sandbox account and save the keys somewhere you both can reach.
  4. Both of you: complete the ADK quickstart — the hello-world agent, nothing more. Two hours, together, on a call. Do not read the whole documentation site.
  5. Agree on Python for the agents and push a first commit to the shared repository.

Leave the 31st empty

The deadline is the 31st. Treat the 30th as the deadline. Every team that plans to finish on the last day discovers something on the last day.

Working rules for a two-person beginner team

  • Learn narrowly. You need one ADK concept — an agent with tools — and one Gemini feature: structured output. Everything else is a distraction until it is required.
  • Prototype prompts in AI Studio first. Getting extraction right is a prompt problem, not a code problem. Solve it in the browser, then paste it into an agent.
  • Write the deterministic agents as plain functions first. Ingestion, Forecast and Strategy are ordinary code. Get them correct standalone, then wrap them as agents. Do not learn a framework and a domain simultaneously.
  • The deployed URL is sacred. If a change breaks it, revert first and diagnose after.
  • Time-box debugging to forty-five minutes. Then swap problems with your teammate or ask. Beginners lose days to single bugs.
  • Fifteen minutes at the start of each day. What you did, what you are doing, what is blocking you. Nothing else.
  • Commit and push at the end of every day, even unfinished. The other person cannot help with work they cannot see.

The three risks most likely to hurt you

  1. The category mapping. Plaid’s taxonomy against the wording in issuer terms. It looks trivial and quietly consumes a weekend. Confirm what sandbox actually returns in week one.
  2. Agent runtime against a four-minute video. A full pipeline pass takes far longer than the demo can afford, and a live call can hang on camera. The paced replay is not a shortcut; it is the responsible choice.
  3. Integrating late. If both of you build agents in isolation until the final week, you will spend that week integrating instead of polishing. The day-three keystone exists precisely to prevent this.
